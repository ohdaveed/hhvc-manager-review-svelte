# Move draft generation off the 60s synchronous ceiling

Today a whole-page draft is generated by a **synchronous** call the browser makes to
`/api/ai/generate`, so it is capped by Netlify's 60s function limit. This plan moves
generation to a Netlify **background function** (15 min) and has the client learn the
outcome from the database rather than from its own response.

Scope is the `content` task (a whole-page draft) only. Field rewrites take ~10s and are
nowhere near the ceiling; leaving them synchronous keeps the fast path fast.

---

## Why this is worth doing, and why it is not urgent

**Measured, from `CLAUDE.md`:** a field rewrite ~10s, a whole-page draft **~46s**,
against a 55s budget (`DEFAULT_DEADLINE_MS`, `src/lib/server/ai/generate.ts:43`) under a
60s hard kill. With the current default model the page draft fits. It fits with 9s to
spare, and one model change spends that: `gemini-3.8-flash` at default thinking measured
138s and 504'd every Rethink.

So the case is not "it is broken today". It is three things:

1. **The margin is one config change wide.** `GEMINI_MODEL` and
   `GEMINI_THINKING_LEVEL` are env vars on the Netlify site; nothing in CI measures
   latency, so the regression surfaces as 504s in production.
2. **Closing the tab strands a draft, and that is a real bug now.** The slow call lives
   in the BROWSER's fetch (`src/lib/stores/draftPages.ts:71`, `generateAndRecord`), not
   on the server. Navigate away and the request aborts, the `PATCH` never happens, and
   the row sits in `drafting` until `DRAFT_STALE_MS` (90s) re-labels it stale. The
   propose form's copy — "you can leave this page while it works" — is not true today.
3. **90s > 60s.** The stale timeout is already longer than the ceiling, so a draft
   killed by Netlify looks "stale", not "failed". The UI is already describing a
   failure mode it cannot distinguish.

---

## The two couplings that make this a port, not a move

A background function is a standalone file under `netlify/functions/`, bundled by
Netlify's own esbuild — **not** part of SvelteKit's single bundled function. There is no
`netlify/` directory in this repo today. The existing AI layer cannot be imported into
one as it stands:

| Coupling                                     | Where                                       | Why it breaks outside SvelteKit                     |
| -------------------------------------------- | ------------------------------------------- | --------------------------------------------------- |
| `import { env } from '$env/dynamic/private'` | `src/lib/server/ai/gemini.ts:1`             | `$env/*` is a SvelteKit virtual module              |
| `import … from '../style/*.md?raw'`          | `src/lib/server/ai/vendor/prompts.js:15-16` | `?raw` is a Vite feature; esbuild has no equivalent |

Both are fixable and neither is deep. They are the actual work.

**`vendor/` is kept mechanically diffable** against
`HHVC_manager_review_current_tool_package` by an explicit rule in `CLAUDE.md`. The `?raw`
fix must not restyle `prompts.js`; see Task 2 for the shape that respects that.

## Tasks

### Task 1 — decouple env (`src/lib/server/ai/`)

Replace `$env/dynamic/private` in `gemini.ts` with a tiny `readEnv()` in
`vendor/env.js`'s sibling — it already owns env parsing (`numberFromEnv`) — resolving
`process.env` and nothing else. SvelteKit's Node adapters populate `process.env`, so the
existing route keeps working unchanged.

Test: the existing `gemini` tests set env vars; add one asserting `GEMINI_BASE_URL`
still redirects to a stub through the new accessor, since that is how the suite avoids
calling the real API.

### Task 2 — decouple the style corpus (`?raw`)

`prompts.js` inlines two markdown files totalling ~28 KB. Make the loader injectable
rather than rewriting the vendored file's logic: keep `prompts.js` importing its strings
from a sibling `style/index.js`, and give that module two builds — the Vite path keeps
`?raw`, the function path reads the files with `fs.readFileSync` and `included_files` in
`netlify.toml`.

The constraint to respect: the diff against the upstream tool package must stay readable.
Changing two import lines is acceptable; restructuring `prompts.js` is not.

Test: assert both loaders return byte-identical strings, so the two paths cannot drift.

### Task 3 — `netlify/functions/draft-background.mts`

Named `*-background` — that suffix is what makes it a background function.

- Verify the caller's bearer token **first and outside the try**, exactly as
  `src/routes/api/ai/generate/+server.ts` does; its comment explains why a SvelteKit
  `HttpError` must not be flattened into a 500, and the same reasoning applies.
- Body: `{ draftId, description }`. Cap it as the route does (the route caps at 64KB;
  background functions cap at **256 KB** regardless).
- Generate with the ported `generate.ts`, **without** the 55s deadline — pass a budget
  sized to the 15-minute limit instead.
- Write the outcome with the service-role key, setting `state` to `ready` or `failed`,
  the same columns `PATCH /api/pages` writes today.
- It returns **202 immediately and cannot return a result.** That is the whole point and
  it is what forces Task 4.

**Retries are automatic and are a hazard here.** Netlify retries a failed background
invocation after 1 minute, then again after 2. A generation that fails halfway could run
three times and spend the Gemini key three times. Make the handler idempotent: re-read
the row and return early if it is no longer `drafting`.

### Task 4 — the client learns from the database

This is new work, not a rewiring: **`draft_pages` is not in the realtime publication.**
`20260822010000` adds `comments` and `edits`, `20260822020000` adds `pages`; nothing adds
`draft_pages`, and `draftPages.ts` opens no channel. Today the client learns the outcome
from its own `PATCH` response.

- Migration: `alter publication supabase_realtime add table draft_pages;`
- Subscribe in `draftPages.ts` to UPDATE events for the current review, replacing the row in
  `draftsStore` — `reviewState.ts:174-205` is the pattern to follow.
- `generateAndRecord` collapses to: POST to the background function, then wait for the
  row to change. Keep `DRAFT_STALE_MS` as the backstop, but **raise it** — 90s was sized
  for a 60s ceiling and is now far too short for a 15-minute budget.

**Remember the merge-to-main behaviour:** this migration applies to production on merge,
and the Supabase GitHub App does **not** touch staging. Push it to staging by hand, or
deploy previews will subscribe to a publication that lacks the table.

### Task 5 — the adapter-node path

`vite.config.ts:20` picks the adapter from `ADAPTER=node`; the Dockerfile uses
adapter-node. **A Netlify background function does not exist in that build.** Decide and
state which:

- keep `/api/ai/generate` working synchronously as the fallback, and have the client use
  the background function only when it is present (feature-detect, do not sniff the
  host); or
- declare the Docker path unsupported for whole-page drafts.

Defaulting to the first. The synchronous route stays for field rewrites regardless, so
nothing is deleted either way.

### Task 6 — tests

- `tests/` unit: the idempotency guard (a second invocation on a `ready` row is a no-op);
  the realtime handler replacing a row; the stale timeout.
- e2e: `tests/signedIn.ts` already stubs realtime with `page.routeWebSocket`, so a
  drafting → ready transition can be driven without a server. Add it to
  `tests/accessibilitySignedIn.e2e.ts`'s draft-state scan only if a new banner state
  appears.
- The e2e fixture gate applies: import `test` from `./fixtures`.

## Alternatives, and why not

**Raise `GEMINI_DEADLINE_MS`.** Does nothing. 55s is ours; 60s is Netlify's and
[the docs list it as not configurable](https://docs.netlify.com/build/functions/configuration/).
Raising ours past theirs trades a clean 504-with-issues for Netlify's own hard kill and
no draft.

**Stream the response.** Looks like the cheap fix and is a trap: a 2026 support thread
reports
[streaming functions hard-terminated at exactly 30s](https://answers.netlify.com/t/streaming-function-hard-terminated-at-exactly-30s-instead-of-documented-60s/172286)
despite the documented 60. That halves the budget.

**[Netlify Async Workloads](https://docs.netlify.com/build/async-workloads/overview/).**
The better long-term fit if this grows multi-step — durable execution, retries, steps
that are not repeated on retry. It is a separate Extension, its internal work bills as
normal function usage, and its
[serverless timeout defaults to 60s and explicitly does not apply to background
functions](https://docs.netlify.com/build/async-workloads/optional-configuration/).
Worth revisiting; too much machinery for one call.

**Supabase Edge Functions.** The service-role key and the database are already there, so
the write is local. Rejected for now because it adds a second deploy target with its own
secrets and its own limits, and the AI layer would still need Tasks 1 and 2.

**Do nothing.** Legitimate. The current default model runs 9–16s. Revisit if the model
changes or if stranded drafts are reported.

## Gates

`bun run verify`, `bun run test:e2e`, and the three ratchets. The new function is outside
`src/`, so confirm `eslint.config.js` and `.svelte-kit/tsconfig.json`'s `include` either
cover `netlify/` or deliberately ignore it — a new top-level directory is exactly how the
eslint count moved on one machine and not another before.

No `verify:live` gate covers generation latency. If this ships, the honest check is a
timed whole-page draft against production, recorded in `CLAUDE.md` beside the existing
measurements.
